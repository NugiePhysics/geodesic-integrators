# 0004. Metric interface: compiled kernels returning full arrays

- Status: Accepted
- Date: 2026-10-07

## Context

[ADR 0001](0001-full-8d-phase-space.md) requires a general metric interface. Adding Kerr must change no line in `formulations/` or `integrators/`. [ADR 0002](0002-numba-first.md) requires everything on the integration path to be Numba-compiled and composed through closures, not `jitclass`. Three questions remained open:

1. **What a metric returns.** Kerr has $`g^{t\phi} \neq 0`$, and later metrics may have other off-diagonal terms (Kerr–Schild, Eddington–Finkelstein). An interface built on $`f(r)`$, like the predecessor's, cannot express them.
2. **Index order.** $`\partial_\alpha g^{\mu\nu}`$ and $`\Gamma^\mu_{\alpha\beta}`$ are both 4×4×4 arrays, and each has two plausible layouts. A silent mismatch between a metric and a formulation would produce plausible-looking wrong orbits.
3. **Where the constants of motion live.** $`E`$ and $`L_z`$ come from Killing vectors that every stationary, axisymmetric metric shares. $`L^2`$ (Schwarzschild) and Carter's $`Q`$ (Kerr) are specific to one metric. Formulation (a) must report them too, although it has no momenta.

## Decision

1. **A metric is five compiled kernels** (`geoint.metrics.MetricKernels`), each a function of a position `x` of shape `(4,)` returning a full array:

   | Kernel | Shape | Entry `[i, j, k]` |
   |---|---|---|
   | `g(x)` | (4, 4) | $`g_{ij}`$ |
   | `g_inv(x)` | (4, 4) | $`g^{ij}`$ |
   | `dg_inv(x)` | (4, 4, 4) | $`\partial_i g^{jk}`$: derivative index first |
   | `christoffel(x)` | (4, 4, 4) | $`\Gamma^i_{jk}`$: upper index first |
   | `invariants(x, p)` | (n,) | constants of motion, named by `Metric.invariant_names` |

   A `Metric` object is a thin Python wrapper around these kernels. It also holds `horizon`, `cyclic_coords`, `invariant_names` and `stop_surfaces()`.
2. **Formulations contract over every index pair** (16 terms for $`g^{\mu\nu}p_\nu`$, 64 for $`\Gamma^\mu_{\alpha\beta}u^\alpha u^\beta`$) and never look at sparsity.
3. **The metric owns its constants of motion** and computes them in the canonical variables $`(x, p_\mu)`$. Formulation (a) lowers $`p = g\,u`$ first. Each formulation adds only the mass shell $`H`$.
4. **Cyclic coordinates are declared** (`cyclic_coords`), and the matching slices of `dg_inv` must be exact floating-point zeros. Tests check this. It is what makes $`p_t`$ and $`p_\phi`$ conserved bit for bit in formulation (b) ([theory §5.2](../theory/formulations.md#5-conserved-quantities)).
5. **Stopping surfaces are data, not code**: `StopSurface(name, index, value, direction)`. The event machinery of Phase 2 turns them into event functions. A per-run value such as the horizon margin then never triggers recompilation.
6. **Kernels are compiled once per parameter set.** The kernel factory is cached on the structural parameters ($`M`$, later $`a`$), and formulation kernels are cached on the metric kernels. Repeated `Schwarzschild(1.0)` objects share compiled code.
7. **Hand-written kernels are verified against `tools/derive_metric.py`** (SymPy), evaluated at 50 significant digits, to a relative error of $`10^{-14}`$ per component. Kerr kernels are to be generated by the same tool.

## Consequences

Positive:

- Kerr needs only a new metric module, with no formulation changes. Off-diagonal paths are already in use: the shell solver in `initial_conditions` is tested on random non-diagonal Lorentzian forms.
- Index conventions are written down once, in `geoint/metrics/base.py`, and enforced by the SymPy comparison and by the eq. (17) consistency test between the formulations.
- One cross-formulation identity test (theory eq. 17) ties `christoffel` and `dg_inv` together. A metric whose two kernels disagree fails it.

Negative, and what we do about it:

- **Allocation and dense contractions in every evaluation.** Each kernel call allocates its output array, and the contractions multiply many structural zeros. On an i5-7300HQ one evaluation of (a) takes about 135 ns and one of (b) about 331 ns, because (b) calls two kernels (`g_inv` and `dg_inv`). This is cheap next to Python overhead, but it is implementation cost, not intrinsic cost. Before wall times are compared across formulations (ADR 0003), a fused kernel or preallocated work arrays will be considered, and only if profiling justifies it.
- **Accuracy depends on how the kernel is written.** The Schwarzschild kernels use $`r - 2M`$, which is exact for $`M \le r \le 4M`$ (Sterbenz lemma), rather than $`f = 1 - 2M/r`$, which loses $`\log_{10}(1/f)`$ digits near the horizon. Generated kernels for Kerr will need the same care, with $`\Delta = r^2 - 2Mr + a^2`$ written in factored form.
- **No input validation inside kernels.** At $`r = 2M`$ or $`\sin\theta = 0`$ they return `inf` or `nan` rather than raising, because Numba kernels cannot raise cheaply. Stopping surfaces keep integrations away from those points (roadmap pitfalls 1–2).

## Alternatives considered

- **The predecessor's `f(r)` protocol.** Rejected: it cannot express off-diagonal metrics.
- **Sparse kernels that return only the non-zero components.** Faster for Schwarzschild, but the sparsity pattern would then be part of the interface, and the formulation code would have to change for Kerr.
- **Christoffel symbols computed at run time from `g_inv` and `dg_inv`.** One kernel fewer per metric, but more arithmetic in every evaluation of (a), and the hand-written symbols would no longer be an independent check of `dg_inv`.
- **`jitclass` metrics.** Rejected in ADR 0002: limited support and harder debugging.
- **JAX autodiff as the source of derivatives.** Kept as an optional cross-check (ADR 0002), not as the primary path.
